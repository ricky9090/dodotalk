# ADR-0009: 优先自建合成映像夹具，而非下载真实映像

## 背景

DodoTalk 目前的自动化测试依赖**用户自备的 Squeak 2.2 映像**。`ADR-0002` 确定了
"测试映像放在仓库外 `temp/test-images/` 并由 `TestImages` 自动发现"，同时**否决**了
"首次运行时自动下载"——理由是网络可达性、来源校验与版权确认三项风险。

该决策留下了两个后果：

1. **回归网不完整**：本地实测（HEAD `b3fa375`，无任何映像）232 个测试中只有 **155 个
   真正执行**，**77 个被整类跳过**（13 个测试类）。更关键的是，**解释器内核**
   （字节码分派、消息发送、方法查找、方法缓存、上下文切换）**没有任何测试真正跑过
   一条字节码**——只有 `SqueakVMContextTest` 里 4 个白盒断言。
2. **无法在 CI 中建立端到端回归网**：`ADR-0002` 否决自动下载，而 CI 既没有用户自备
   映像，也不适合在 workflow 里静默下载外部资产。

同时还有两个更基础的问题：

3. **没有性能刻度**：`RuntimeStats` 只统计原语调用，不统计字节码/发送次数，因此任何
   性能改动都无法证明它更快，也没有证明它没变慢。
4. **格式知识只被单向验证**：2.2 映像格式知识散落在 `SqueakImage` / `SqueakObject` /
   `Squeak.java` 中，只在**读**的方向被生产代码覆盖过。

此外，2026-11-02 的战略评估提出了一个更长远的问题：能否最终**不再依赖 Squeak 2.2
作为运行时基线**，转而使用 DodoTalk 自己的映像。该评估的结论是：

> **夹具解决的是"容器"（二进制格式 + 对象表 + 读写机制），不解决"内容"。**
> 真实 2.2 映像 = 70,200 个对象，其中 **15,643 个 CompiledMethod**（516,324 字节
> 字节码 = 堆的 14.4%）、约 **42,264 个方法槽**、**1,063 个类**。
> **内容就是 Smalltalk 系统本身**，手写它等于自己写一个编译器 + 一套类库。

因此本 ADR 需要同时做两件事：把"自建夹具"这一决策固化下来，并**明确它不覆盖**
"造含 Smalltalk 库的新映像"这一更大命题。

## 决策

1. **自建合成夹具优先于下载真实映像。** 在 `src/test` 中实现一个**独立实现 Squeak 2.2
   二进制格式**的最小写入器，生成可被 DodoTalk 启动并执行字节码的合成映像，作为
   解释器内核的回归基座与确定性性能刻度负载。

2. **生成器不复用 `SqueakImage.writeImage`。** 生成器与生产 reader **不得共用实现**，
   否则两处同时写错时测试仍然全绿，夹具将失去主要价值。生产 writer 另由一条
   "save → reload → 再执行 → 结果不变"的往返用例覆盖。

3. **生成物不落仓库，每次测试运行现场生成。** 既避免 `checkNoSqueakImages` 命中，
   也保证每次运行都重新生成生成器本身、持续验证其正确性。

4. **零生产代码改动、零第三方资产。** 只使用已有的 public 入口与测试自身可访问的
   包级成员；停机用未实现操作码（126/127 → `nonoBytecode`）作为陷门。

5. **合成夹具不替代真实映像测试。** UI、MVC、真实 Form、原语全表、copyBits、
   scanCharacters 等覆盖仍需用户提供真实映像。`ADR-0002` 的"用户自备映像"流程
   保持不变。

6. **刻度只记录、不设阈值断言。** 同一负载在 CI 机器、开发机、笔记本上的速率差异
   可达数倍，硬性速率断言只会产生跨机器假红。刻度的作用是"改动前后**同一台机器**
   上的可比性"。

7. **本 ADR 不为"自造含 Smalltalk 库的新映像"开绿灯。** 任何从 2.2 派生的映像都
   携带 2.2 **内容**的版权归属；clean-room 路线是多年工程。该方向的决策必须由
   **单独的 ADR** 明确，本 ADR 只声明"未决"。

8. **本 ADR 是 `ADR-0002` 的补充，不取代它。** `ADR-0002` 仍然有效：真实映像放在
   仓库外、自动发现、首次运行不自动下载。

## 后果

### 正面

- 解释器内核第一次拥有**端到端可执行**的自动化覆盖（字节码分派、原语字节码、消息
  发送、方法查找与缓存、上下文切换、返回）。
- `./gradlew clean test` 的**有效执行数**从 155 提高，且这批用例**不需要任何外部
  资产**，因而具备进入 CI 的条件。
- 获得一个**确定性的性能刻度**，使"改动是否变慢"成为可回答的问题。（该刻度已实际
  用于一次结论修正：见下方"已产生的一个结论修正"。）
- 2.2 映像格式获得一个**端到端可执行的规格载体**：生成器独立于生产 reader 实现
  格式，因此生产 reader 被持续反向校验。
- 一旦有了"能独立写出合法 2.2 映像"的机器，"往映像里注入 / 替换对象"就有了机械
  基础——这是长期摆脱"运行时依赖 Squeak 2.2"的必经之路。

### 负面

- **重复实现了一部分格式知识**（约 250 行）。生产 reader 若变更格式，生成器可能
  失效——缓解措施是格式常量集中 + 同步到 `doc/specifications/image/image-format.md`，
  且 reader 一旦变更夹具会立即变红（**响亮地失败**，而非静默通过）。
- **覆盖度可能被高估**。合成映像只有 25–31 个对象，没有 Smalltalk 库、没有 MVC。
  必须同时在 Issue、Design 与 PR 描述中写明，避免把"新增 N 个测试"读成"端到端覆盖
  已完备"。
- **性能刻度有被误用为门禁的风险**。一旦有人把速率阈值写进 CI，会立刻退化成
  跨机器假红。
- **单点维护成本**：格式知识有两处（生产 reader、生成器）。这是刻意的重复。

### 中性

- 不改变 `ADR-0002` 的任何条款；真实映像测试的可用性与跳过逻辑保持原样。
- 合成夹具**不**替代真实映像，两者互补。
- 本 ADR 不改变 `checkNoSqueakImages` 的语义。

### 已产生的一个结论修正（附环境备注）

本 ADR 确立的刻度曾被用于修正一条此前的判断：

| 项 | 修正前 | JDK 17 云端沙箱（3 轮） |
|----|--------|--------------------------|
| 字节码分派是否最大性能天花板 | 是（列为最大性能天花板） | **否**。表分派 ≈ **70M bytecodes/s**；手写 `switch` ≈ 28M/s，慢约 2.3× |

但 2026-11-02 在**项目基线 JDK 25 + 本地开发机**上用同一组脚本复测，方向相反：

| 分派方式 | JDK 25 本地（3 轮） |
|----------|----------------------|
| `BytecodeExcutor[]` 表 + lambda | 180.18M / 175.86M / 169.15M bytecodes/s |
| 手写 `switch`（4 个操作码） | 220.82M / 218.98M / 209.38M bytecodes/s |

两次实验的 JDK、硬件、操作系统与运行方式均不同，不能把差异归因于单一变量。
因此：

- **不能**把“表分派 70M/s、switch 慢 2.3×”当作跨环境结论；
- **分派改造的优先级暂缓**，先完善 benchmark 设计（固定 JDK/机器、预热、多轮、
  中位数、区分测试侧手动循环与 `SqueakVM.run()`、明确操作码覆盖范围）；
- 分派改造仍可能因**可维护性**值得做，但不应以这组环境不可比的数据作为 P0 依据；
- `bench` 变体只保留确定性执行步数/栈平衡断言，不设耗时或吞吐阈值。

> 记录位置：原始脚本见 `../temp/patches/ISSUE-0011/bench-measurements/`
> （仓库外，不随 ADR 提交）。后续 benchmark 设计应单独立 Issue/ADR，不在本 ADR
> 内追加门禁。

## 备选方案

| 方案 | 结论 | 理由 |
|------|------|------|
| A. 测试侧独立写入器（**采用**） | 采用 | 零版权问题、确定性、无外部资产；代价是重复实现一小部分格式知识，换来生产 reader 的独立校验 |
| B. CI 从 files.squeak.org 下载真实映像 | 不采纳（作为后续单独议题） | 覆盖最全，但需要单独的来源校验与版权声明；`ADR-0002` 已否决"首次运行自动下载"，CI 场景不同，但不能默默在 workflow 里下载 |
| C. 提交裁剪后的 mini image | 否决 | 裁剪不改变版权归属；且 `checkNoSqueakImages` 会直接命中 |
| D. 只做白盒单元测试 | 否决 | 覆盖不到字节码分派、消息发送与上下文切换——恰是解释器内核最需要回归保护的部分 |
| E. 复用 `SqueakImage.writeImage` 作为生成器 | 否决（仅保留为往返用例） | 生成器与 reader 共用实现则失去独立校验价值 |
| F. 在生产代码加 `SqueakVM.run(int)` 或字节码计数器 | 暂不做 | 会改动生产代码路径；测试侧计数已足够。若后续提出，需单独立 Issue 讨论 |
